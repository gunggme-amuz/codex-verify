# Codex Verify: 독립적 코드/계획 검증 스킬

## 개요

이 스킬은 OpenAI Codex CLI를 "두 번째 눈"으로 활용한다. Claude가 작성한 코드나 계획을 Codex가 독립적으로 검증함으로써, 단일 모델의 편향이나 맹점을 보완한다. 이는 코드 리뷰에서 "작성자가 아닌 다른 사람이 리뷰해야 한다"는 원칙과 같다.

## 사전 조건

- `codex` CLI가 설치되어 있어야 한다 (`npm i -g @openai/codex` 또는 `brew install --cask codex`)
- OpenAI 인증이 완료되어 있어야 한다 (API key 또는 ChatGPT 로그인)

## 검증 유형

사용자의 요청과 맥락에 따라 아래 중 적절한 검증 유형을 선택한다:

### 1. 코드 리뷰 (code-review)
작성된 코드의 정확성, 보안, 성능, 가독성을 점검한다.

### 2. 테스트 검증 (test-verify)
테스트가 존재하면 실행하고, 테스트 커버리지와 누락된 엣지 케이스를 확인한다.

### 3. 계획 검증 (plan-verify)
구현 계획의 실현 가능성, 누락된 단계, 잠재적 위험을 평가한다.

### 4. 보안 점검 (security-check)
OWASP Top 10 등 알려진 보안 취약점 패턴을 탐지한다.

## 실행 흐름

### Step 1: 검증 대상 파악

사용자에게 무엇을 검증할지 확인한다. 대부분의 경우 현재 대화에서 작업한 파일들이 대상이다.

- 변경된 파일 목록을 `git diff --name-only`로 확인
- 새로 생성된 파일은 `git status`로 확인
- 사용자가 특정 파일이나 디렉토리를 지정하면 그것을 사용

### Step 2: 검증 프롬프트 구성

검증 유형에 맞는 프롬프트를 구성한다. 프롬프트는 구체적이고 구조화되어야 Codex가 유용한 결과를 반환한다.

**코드 리뷰 프롬프트 템플릿:**
```
다음 파일들을 리뷰해줘: {파일목록}

다음 관점에서 검토하고, 각 항목별로 [PASS], [WARN], [FAIL] 태그를 붙여서 결과를 알려줘:

1. 정확성: 로직 오류, 오프바이원 에러, null/undefined 처리
2. 보안: 인젝션, XSS, 하드코딩된 시크릿, 안전하지 않은 디시리얼라이제이션
3. 성능: 불필요한 반복, N+1 쿼리, 메모리 누수 패턴
4. 엣지 케이스: 빈 입력, 극단값, 동시성 문제
5. 코드 품질: 네이밍, 중복, 단일 책임 원칙

문제가 없으면 "ALL CLEAR"라고 명시해줘.
```

**테스트 검증 프롬프트 템플릿:**
```
다음 프로젝트의 테스트를 검증해줘: {디렉토리}

1. 기존 테스트를 실행하고 결과를 보고해줘
2. 테스트가 없는 핵심 함수를 식별해줘
3. 누락된 엣지 케이스 테스트를 제안해줘

결과를 [PASS], [WARN], [FAIL] 태그로 구분해줘.
```

**계획 검증 프롬프트 템플릿:**
```
다음 구현 계획을 검토해줘:

{계획 내용}

다음을 평가해줘:
1. 실현 가능성: 기술적으로 구현 가능한가?
2. 완전성: 누락된 단계가 있는가?
3. 의존성: 순서가 올바른가? 순환 의존이 없는가?
4. 위험: 실패 가능성이 높은 단계는?

각 항목에 [PASS], [WARN], [FAIL] 태그를 붙여줘.
```

### Step 3: Codex 실행

```bash
codex exec "{프롬프트}" 2>/dev/null
```

**주의사항:**
- `codex exec`는 비대화형 모드로 실행된다
- stderr에 진행 상황이 출력되므로 `2>/dev/null`로 억제한다
- 결과는 stdout으로 반환된다
- 타임아웃은 최대 300초(5분)로 설정한다

### Step 4: 결과 파싱 및 판정

Codex의 응답에서 태그를 파싱한다:

| 태그 | 의미 | 조치 |
|------|------|------|
| `[PASS]` | 문제 없음 | 다음 항목으로 진행 |
| `[WARN]` | 경미한 이슈, 개선 권장 | 사용자에게 보고, 수정 여부는 사용자 결정 |
| `[FAIL]` | 심각한 문제 발견 | 즉시 수정 필요, 루프 계속 |
| `ALL CLEAR` | 모든 항목 통과 | 검증 완료 |

### Step 5: 검증 루프

검증은 반복적으로 수행될 수 있다. 아래 조건에 따라 루프를 관리한다.

#### 루프 진입 조건
- `[FAIL]` 태그가 하나 이상 존재할 때
- 사용자가 발견된 `[WARN]` 항목의 수정을 요청했을 때

#### 루프 내 동작
1. 발견된 이슈를 사용자에게 보고한다
2. 사용자의 확인을 받고 수정을 진행한다
3. 수정 후 동일한 검증을 다시 실행한다
4. 새로운 결과를 이전 결과와 비교한다

#### 루프 탈출 조건 (하나라도 만족하면 종료)

| # | 조건 | 설명 |
|---|------|------|
| 1 | **ALL CLEAR** | 모든 검증 항목이 통과 |
| 2 | **최대 반복 횟수 도달** | 기본 3회. 무한 루프 방지. 사용자가 조정 가능 |
| 3 | **진전 없음** | 이전 반복과 동일한 이슈가 재발견됨 (같은 문제가 2회 연속 나타나면 중단) |
| 4 | **FAIL 없음** | FAIL이 0개이고 WARN만 남은 경우 (WARN은 권고사항) |
| 5 | **사용자 중단** | 사용자가 명시적으로 "그만", "충분해", "넘어가자" 등을 말함 |
| 6 | **Codex 오류** | Codex CLI가 에러를 반환하거나 타임아웃 (재시도 1회 후에도 실패하면 중단) |

#### 루프 상태 보고

각 반복마다 사용자에게 진행 상황을 간결하게 보고한다:

```
[검증 라운드 2/3]
- PASS: 3개 항목
- WARN: 1개 항목 (SQL 쿼리 파라미터화 권장)
- FAIL: 0개 항목
→ FAIL 없음, 검증 완료.
```

### Step 6: 최종 보고

검증이 완료되면 결과를 요약한다:

```
## Codex 검증 결과

| 항목 | 결과 | 비고 |
|------|------|------|
| 정확성 | PASS | - |
| 보안 | WARN | SQL 파라미터화 권장 |
| 성능 | PASS | - |
| 엣지 케이스 | PASS | - |
| 코드 품질 | PASS | - |

총 라운드: 2회
최종 판정: PASS (WARN 1건 존재)
```

## 중요 원칙

1. **Codex는 보조 도구이지 최종 판단자가 아니다.** Codex의 지적이 항상 옳은 것은 아니며, Claude의 판단과 사용자의 결정이 우선한다. Codex가 false positive를 낼 수 있으므로, 맹목적으로 모든 지적을 수정하지 말고 타당성을 먼저 평가한다.

2. **사용자의 시간을 존중한다.** 사소한 스타일 이슈로 루프를 반복하지 않는다. FAIL 수준의 문제만 자동으로 수정 루프를 돌린다.

3. **투명하게 동작한다.** Codex에 보내는 프롬프트와 받은 응답을 사용자가 확인할 수 있게 한다. "뒤에서 알아서" 하지 않는다.

4. **컨텍스트를 전달한다.** 검증 프롬프트에 프로젝트의 기술 스택, 사용 언어, 프레임워크 정보를 포함하면 Codex가 더 정확한 결과를 반환한다.
